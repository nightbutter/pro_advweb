# Database Migration: SQLite → Neon PostgreSQL

## 1. Original vs Target

| | Before | After |
|---|---|---|
| Engine | SQLite 3 (single file `server/database.sqlite`) | PostgreSQL hosted on Neon |
| Driver | `better-sqlite3` (synchronous, native module) | `pg` (node-postgres, pure JS, async) |
| ORM | none — raw SQL | none — raw SQL (unchanged approach) |
| Migrations | `CREATE TABLE IF NOT EXISTS` at startup | `migrations/*.sql` + `npm run migrate`; runtime init shares the same DDL via `server/schema.ts` (byte-equivalence enforced by test) |
| Auth | JWT via `users` table (scrypt hashes) | unchanged — same `salt:hash` format, `users` now lives in Postgres |
| Env config | none | `DATABASE_URL`, `DATABASE_URL_UNPOOLED`, `JWT_SECRET`, `ADMIN_PASSWORD`, `RIDER_PASSWORD`, `CORS_ORIGINS` |

No background jobs; all raw SQL lives in `server/dbconnect.ts`, `server/controller`, `server/scripts` and `server/migrations`. The Angular client talks to the API over HTTP only (JWT interceptor unchanged) — no frontend changes were required.

## 2. Architecture & Connection Flow

- `server/dbconnect.ts` creates a single `pg.Pool` from `DATABASE_URL`.
  - Pool size: `10` locally, `3` on Vercel (`VERCEL` env), override with `PGPOOL_MAX`.
  - SSL: if the URL contains `sslmode=`/`uselibpqcompat=` the URL drives TLS. Otherwise localhost URLs get `ssl: false` and remote hosts get `ssl: { rejectUnauthorized: true }` (Neon requires TLS).
  - An `error` handler on the pool prevents an idle-client disconnect (e.g. Neon autosuspend) from crashing the process.
- `transaction(fn)` wraps `BEGIN`/`COMMIT`/`ROLLBACK` on a dedicated client — used by schema init+seeding, `POST /orders/simulate`, `POST /routes/optimize` and `DELETE /customers/:id`.
- `initDatabase()` runs inside `pg_advisory_xact_lock(727201)`; every request waits for the readiness gate (`ensureDb` in `server/app.ts`), which returns `503` (never crashes) on init failure and retries on the next request.
- `POST /orders/simulate` serializes concurrent runs with `pg_advisory_xact_lock(727202)` — last-writer-wins, both requests succeed.
- `npm run migrate` holds a session `pg_advisory_lock(727203)` so concurrent invocations serialize.
- `orderNumber` generation uses the `order_number_seq` DB sequence — unique under concurrent inserts.

## 3. Environment Variables

Copy `server/.env.example` → `server/.env`:

| Variable | Purpose |
|---|---|
| `DATABASE_URL` | Neon **pooled** connection (host contains `-pooler`), used by the app. Suffix `?sslmode=require`. |
| `DATABASE_URL_UNPOOLED` | Neon **direct** endpoint, used by `npm run migrate` / `migrate:data` / `check:target`. Falls back to `DATABASE_URL` if unset. |
| `JWT_SECRET` | Required in production — module refuses to load without it. |
| `ADMIN_PASSWORD` / `RIDER_PASSWORD` | Seed passwords; required in production (local dev defaults exist). |
| `CORS_ORIGINS` | Comma-separated allowed frontend origins. |
| `PORT` | Optional, default `3000`. |
| `PGPOOL_MAX` | Optional pool size override. |
| `SQLITE_PATH` | Optional override for `migrate:data` source file (default `server/database.sqlite`). |

Never commit `.env` — it is gitignored. `.env.example` contains placeholders only.

## 4. Schema (PostgreSQL)

Tables: `customers` (with `zone` CHECK — `ขามเรียง`/`ท่าขอนยาง`/`หน้าป้าย`), `orders`, `riders`, `users` (JWT accounts, `role` CHECK — `admin`/`rider`/`customer`, `riderId` → `riders`), `customer_profiles` (`userId` → `users` ON DELETE CASCADE, from migration 003), plus `order_number_seq` and indexes `idx_orders_customer`, `idx_orders_rider`, `idx_users_lower_username` (case-insensitive username uniqueness).

| SQLite | PostgreSQL | Notes |
|---|---|---|
| `INTEGER PRIMARY KEY AUTOINCREMENT` | `INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY` | `BY DEFAULT` (not `ALWAYS`) so explicit IDs can still be inserted during data transfer |
| `REAL` | `DOUBLE PRECISION` | lat/lng |
| `TEXT`, `INTEGER`, `CHECK`, `UNIQUE`, `FK` | unchanged | all constraints preserved |
| `orderTime TEXT DEFAULT CURRENT_TIMESTAMP` | `TEXT DEFAULT (to_char(CURRENT_TIMESTAMP,'YYYY-MM-DD HH24:MI:SS'))` | keeps the text timestamp format; every insert supplies the value anyway |

- camelCase columns are kept and **double-quoted** in SQL so JSON response keys are unchanged.
- Canonical DDL: `server/migrations/001_init.sql` + `002_order_number_seq.sql` + `003_customer_registration.sql`. The runtime path executes `server/schema.ts` (serverless-safe, no filesystem reads); `migrations.test.ts` asserts byte-equivalence for all three migrations and schema-fingerprint parity, so the two paths cannot drift.
- Legacy cleanup: customers matching the old synthetic `081-234-56xx` phone block are deleted **only when ≥20 rows match** — the full old seed set, never a few user-entered rows.

## 5. Command Reference

```bash
cd server
npm install
npm run migrate        # apply migrations/*.sql (advisory-locked, reports target + pending)
npm run migrate:data   # optional: copy rows from database.sqlite -> Postgres
npm run dev            # start API (auto-creates schema + seeds if empty)
npm run build          # tsc -> dist/
npm run test           # full embedded-Postgres suite
npm run test:smoke     # embedded-Postgres end-to-end API test (no PG install needed)
npm run check:db       # connectivity diagnostic (SELECT 1, identity, TLS)
npm run check:target   # read-only schema/row-count verification of the configured target
```

Migration tracking lives in `_migrations`; re-running `migrate` skips applied files.

## 6. Data Transfer

No data transfer was required for this migration: the repository contains no `database.sqlite` (verified — file never committed), and the app regenerates identical seed data (13 riders, 60 customers, 30 orders, 14 users) on first start.

If you have a real `server/database.sqlite` (e.g. an existing local deployment), run `npm run migrate:data` after `npm run migrate`. It copies `customers` (incl. `zone` when present), `riders`, `orders` and `users` inside one transaction with `ON CONFLICT (id) DO NOTHING` (re-runnable), then advances the identity sequences past the max imported ID and prints source/target row counts. Requires Node ≥ 23.4 (uses built-in `node:sqlite`). The source file is opened read-only and never modified.

## 7. Local Development

Easiest: `npm run test:smoke` boots an embedded Postgres (downloaded by the `embedded-postgres` devDependency, UTF-8 forced), applies migrations, starts the app, logs in and runs 23 endpoint assertions. For a persistent local DB, install Postgres or point `DATABASE_URL` at a free Neon dev branch — `sslmode=disable` is accepted for localhost URLs.

## 8. Deployment (Vercel)

1. Create a Neon project; copy the pooled (`-pooler`) and direct connection strings.
2. In Vercel → Project → Environment Variables set `DATABASE_URL`, `JWT_SECRET`, `ADMIN_PASSWORD`, `RIDER_PASSWORD`, `CORS_ORIGINS` — and `DATABASE_URL_UNPOOLED` if you plan to run `migrate` from CI.
3. Import the repo with **Root Directory = `server`**, deploy, then run `npm run migrate` locally/CI against the production unpooled URL (one deliberate step).
4. Point `client/src/app/services/api.service.ts` `baseUrl` at `https://<project>.vercel.app/api`.

`pg` is pure JavaScript — no native compilation on Vercel (the previous `better-sqlite3` node-gyp build issue is gone).

## 10. Known Limitations / Remaining Steps

- `neon.test.ts` destructive/integration suite requires a dedicated Neon test branch (`NEON_TEST_URL`, `NEON_TEST_URL_UNPOOLED`) — intentionally skipped otherwise; embedded-PG pass is not proof of full Neon integration.
- `orders.assignedRiderId` has no FK to `riders` — faithful to the original schema; add `REFERENCES riders(id)` later if desired.
- `latestPlan` route cache is in-memory per instance; on serverless it can reset between invocations — call `POST /api/routes/optimize` first.
- `orders.orderTime` remains `TEXT` to preserve the `'HH:MM:SS'` API format.
- Rotate the Neon password if it was ever exposed outside `.env`.

## 11. Rollback

- The old code is untouched in git history (`git log`); to roll back, check out the previous commit.
- To reverse a migrated Neon DB: export via `pg_dump`/`COPY ... TO CSV`; the schema maps 1:1 back (`IDENTITY` → `AUTOINCREMENT`, `DOUBLE PRECISION` → `REAL`).
- `migrate-data` never deletes from the source SQLite file (opened read-only), so the original data remains intact as a backup.
